Who can contribute

Anyone in Design, Development or Marketing can propose a change. Design owns the system and makes the final call on visual and interaction changes; Marketing owns content limits; Development owns implementation.

How a change gets into WDS

  1. Propose. Describe the need, the pages it affects and why an existing component or section doesn't work. Check the docs first: it may already exist.
  2. Design in Figma. Build it in the WDS 3.0 file using existing variables and text styles, with desktop, tablet and mobile variants and both themes.
  3. Document. Copy the matching page template and fill in every section, including limits and the acceptance checklist. Mark it Proposed.
  4. Review. Get cross-functional review when the change affects visual design, behaviour, accessibility or content limits (see Governance).
  5. Build. Add the CSS to css/wds.css and a live example in src/pages/examples. Run npm run check.
  6. Release. Change the status to Stable, add a Changelog entry and merge.

Changing tokens

  1. Change the variable in Figma, never in css/tokens.css.
  2. Re-export the collection with scripts/figma-export.js and update tokens/wds-tokens.json.
  3. Run npm run build. The Colour page's contrast checks update automatically, so look for new failures.
  4. Renaming or removing a token is a breaking change (see Versioning).

Working in this repository

  • Branch from main, one change per pull request. Vercel builds a preview for every pull request.
  • Page content lives in src/pages. The sidebar is src/nav.json. See the README for structure and shortcodes.
  • Write in the voice described in Voice & tone: plain, specific, second person.
